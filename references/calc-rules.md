# KPI計算ルール（TKC科目残高データ）

このファイルは、TKC形式の科目別月次推移表から経営KPIを算出する際の標準ルールをまとめたもの。
とあるグループ会社向けに固まったルールをベースに、他のグループ会社にも
適用できるよう一般化している。会社ごとに科目コードが違う場合は、下記の「会社ごとに要確認の項目」
を実データで確認してから使うこと。

## 1. データの読み方（共通）

TKC科目残高データは以下の構造を持つ：
- 1列目：科目コード（4桁）。4xxx=収益、5xxx=製造原価、6xxx=販管費、7xxx=営業外
- 2列目：固変区分フラグ。「Ｖ」＝変動費、「Ｆ」＝固定費、それ以外（空白／－／＊）＝どちらでもない
  （＊は期首・期末棚卸高や他勘定振替高など、固変集計の対象外科目によく使われる）
- 3列目：勘定科目名
- 4列目以降：3列1組（借方・貸方・残高）が月ごとに繰り返す。ヘッダー行に「令和X年Y月」や
  「R X. Y」のような和暦表記が入っていることが多い
- 「借方」「貸方」は**その月単体の発生額**（累計ではない）。「残高」は期首からの累計で、
  検算にのみ使う
- 当月発生高の計算：
  - 収益科目（4xxx）：貸方－借方
  - 費用科目（5xxx・6xxx）：借方－貸方

`scripts/extract_tkc_kpis.py` の `find_month_columns()` が月ヘッダー行を解析して
借方/貸方列のインデックスを自動で返す。

## 2. KPI定義（既定値。導入第1社で確定済みのルール）

- **売上高**：科目コード4111〜4115（製品売上高・売上高・売上値引戻り高）の当月発生高の合計
- **変動費計**：固変フラグが「Ｖ」の科目の当月発生高の合計（科目コードを個別に選ばず、
  必ずフラグを起点に機械的に集計する。運賃や電力費など一見変動費に見える科目でも、
  フラグが「Ｆ」ならＦとして扱う）
- **限界利益** ＝ 売上高－変動費計
- **限界利益率**（％）＝ 限界利益 ÷ 売上高
- **人件費**：以下の科目コード（固定リスト。固変フラグだけでは「Ｆの中の人件費」までは
  絞り込めないため、ここだけはコード指定）
  - 製造原価側：5431賃金、5432賞与、5433雑給、5434法定福利費、5435厚生費、5438退職金
  - 販管費側：6111給与手当、6211役員報酬、6212事務員給与、6213従業員賞与、
    6312法定福利費、6226厚生費
- **付加価値額（控除法）** ＝ 限界利益（＝売上高－変動費計。加算法は使わない）
- **労働分配率**（％）＝ 人件費 ÷ 付加価値額

### 会社ごとに要確認の項目
別会社のデータに切り替えるときは、以下を必ず実データで確認する（推測で流用しない）：
1. 売上科目のコード範囲が4111〜4115で一致しているか（別レンジなら実際の科目一覧を提示してユーザーに確認）
2. 人件費12科目のコードが同一体系で存在するか（勘定科目名は多少違ってもよいが、コードと
   金額の対応が取れることを確認する）
3. 固変フラグの表記が「Ｖ」「Ｆ」（全角）で統一されているか

## 1-b. 複数部門・複数事業部のTKCファイル

同じ会社でも、1つのTKCファイルに複数部門・複数事業部のデータがまとめて入っていることがある。
典型的なパターンは以下の2つ：

- **部門列が追加されている**：科目コード列の左に「部門」列（部門コード）が挿入され、
  それより右の列（科目・固変・勘定科目名・借方貸方残高）が通常より1列ずつ右にずれる。
  `find_month_columns()`/`compute_monthly_kpis()`はどちらも列番号を引数で渡す設計なので、
  ずれた分だけ`code_col`/`flag_col`をずらして呼べばよい（コード変更は不要）
- **1シート内に部門ごとの表が縦に連結されている**：部門が変わるたびに、会社名・月ヘッダー・
  列見出し行がその都度再掲される。空白行やヘッダー文字列の再出現を手がかりに、部門ごとの
  データ開始行・終了行を特定し、`compute_monthly_kpis(data_start_row=..., data_end_row=...)`を
  **部門の数だけ呼び分ける**。部門コード列の値（例：B/C/G）でどの部門かを識別できることが多いので、
  先にopenpyxl/xlrdで部門コード列の値がどこで変わるかを確認してから範囲を決める

このパターンに気づかず全行をまとめて集計すると、部門をまたいで数値が合算されてしまい、
KPIが意味を持たなくなる（例：3部門の売上高が1つの数字に混ざる）。**部門ごとに個別のKPIを計算し、
個別のPowerPointファイルとして出力する**のが正しい扱い——1枚のスライドに複数部門を無理に
詰め込まない（KPIカードの意味が「会社全体」なのか「一部門」なのか曖昧になるため）。
部門構成の認識が合っているか（何部門あるか、部門名は何か）は必ずユーザーに確認する。

## 3. 期間比較のルール

- **当月**：データが存在する最新月。ただし直近月の数値が明らかに未確定（きりの良い概算値・
  他の月と乖離が大きい等）に見える場合は、その月を「当月」扱いせず、ユーザーに確認する
  （詳細は `SKILL.md` の「直近月データの信頼性チェック」を参照）
- **前月比**：金額指標（受注高・売上高）は増減率（％）、比率指標（限界利益率・労働分配率）は
  ポイント差（pt）
- **直近3ヶ月平均**：直近3ヶ月分の単純平均。比率指標も「各月の比率をそのまま単純平均」する
  （3ヶ月合計から再計算する加重平均ではない）。この方式はやや簡略化した近似であることを
  出力時にひとこと明記するとよい
- **3ヶ月平均の前期間比**：直近3ヶ月平均 と その直前3ヶ月平均 の比較。金額指標は増減率、
  比率指標はポイント差
- **目標対比**：（実績－目標）／目標。目標値は必ずユーザー入力値を使う。AI側で推測・算出しない。
  限界利益率・労働分配率には目標欄を設けない（目標対比欄は「－」とする）

## 4. 受注高・会社特有の指標について

TKC科目残高データには受注情報が含まれないため、別途「受注実績」データ（月次の受注高・売上高
実績、会社によってフォーマットが大きく異なる）が必要。以下がなければ「データ不足」と明記し、
数値を推測しない：
- 受注高そのもの → 受注実績データがファイルとして一切提供されない場合は、KPIカード・
  チャートから受注高を完全に外す（`kpis`を3枚、`charts`を2枚にする。「－」や0で埋めるのは
  「データはあるが値がゼロ」に見えてしまうため誤り。存在しないなら項目ごと出さない）
- 目標値 → ユーザーから聞く。未回答なら「目標未設定」。シート上に「目標」らしき列が
  あっても、実績と桁感が合わない・別の前提（値上げ分の織り込みなど）が疑われる場合は
  鵜呑みにせずユーザーに確認する（詳細は上記2節）
- 取引先別の受注TOP10・その他会社特有の指標（設備稼働率、不良率など） → 元データが無ければ
  「データ不足」と明記し、資料の構成自体は残す（「今回対象外」と分かるように）。
  データがあり出す場合は`build_deck.js`の`extraSection`（表 or 箇条書き、詳しくは
  `design-system.md`）に載せる。会社によって欲しい指標が違って当然なので、都度ユーザーに
  「今回はどの指標を載せますか」と確認してよい

## 5. 厳守事項

- 存在しないデータ（受注高・目標値・前期間データ）を絶対に推測で埋めない
- 固定費・変動費の集計は必ずＦ／Ｖフラグを参照する。科目コードを見て「これは変動費っぽい」と
  自己判断でＶ／Ｆを割り当てない
- 金額は千円単位で表示し、比率指標のポイント差と金額指標の増減率（％）を混同しない
- 複数部門・複数事業部が1ファイルに入っている場合、部門をまたいで合算しない（1-b節参照）。
  「会社全体」の数字が欲しいのか「部門別」の数字が欲しいのかが曖昧なときはユーザーに確認する
- 所見（insights）で「◯ヶ月で最高値」「過去最低水準」のような順位・最大最小の主張を書くときは、
  必ず対象期間の系列データを実際にソートして確認してから書く。値が大きい／小さいという印象だけで
  書くと誤りやすい（実例：単月の受注高が18ヶ月中3番目に高いだけなのに「最高値」と書いてしまった
  ケースがあった。QAで数値の一致は確認していても、この種の相対的な主張は見落としがち）
